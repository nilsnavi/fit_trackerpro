# Вход по email

В браузере и PWA пользователь запрашивает код, вводит его и получает обычную пару access/refresh JWT. Подтверждённый новый адрес создаёт аккаунт. Пользователь Telegram может один раз привязать адрес из авторизованного профиля и затем входить в тот же аккаунт.

- `POST /api/v1/users/auth/email/request` принимает `email`, возвращает `challenge_id`. `POST /email/verify` принимает `challenge_id` и `code`.
- `POST /api/v1/users/auth/email/link/request` и `POST /email/link/verify` требуют действующей сессии. Код привязан к аккаунту и назначению. Адрес другого аккаунта нельзя присвоить или использовать для слияния аккаунтов.
- Код шестизначный, действует 10 минут, допускает пять попыток и погашается при использовании. Новый код можно запросить через минуту. Запрос ограничен по IP и адресу. Сервер хранит HMAC, письма отправляются по SMTP с TLS.
- Для запуска задаются `AUTH_SMTP_HOST`, `AUTH_SMTP_FROM`, при необходимости `AUTH_SMTP_PORT` (по умолчанию 587), `AUTH_SMTP_USERNAME`, `AUTH_SMTP_PASSWORD`. Без SMTP запрос возвращает 503.
- Для email-аккаунта без Telegram `telegram_id` равен null. Существующие Telegram JWT сохраняют свой идентификатор. Email-only JWT используют отдельный диапазон подписанного идентификатора, основанный на внутреннем ID.
- Приёмка: новый email, повторный вход и refresh, сохранение ID при привязке, отказ для чужого адреса, повторно использованного и просроченного кода, Telegram-регрессия и production Playwright.

В этом изменении браузер сохраняет действующий формат сессии: токены живут в памяти вкладки, после полной перезагрузки вход по коду повторяется. При смене аккаунта на устройстве приложение очищает общий кэш, а при наличии незавершённой тренировки просит сначала синхронизировать её из прежнего аккаунта.

Перед включением доставки нужно проверить письмо с реальным SMTP на staging и убедиться, что frontend и API используют текущие правила CORS. Откат после регистрации email-аккаунтов выполняется отключением доставки при сохранении миграции.
