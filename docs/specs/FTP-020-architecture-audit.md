# FTP-020 — FitTracker Pro 2.0 Architecture Audit (SPEC)

**Статус:** ✅ завершено (2026-11-18)
**Ветка:** `feature/ftp-020-architecture-audit`
**Тип:** audit / planning (без изменений рабочего приложения)
**Вход:** репозиторий `nilsnavi/fit_trackerpro` @ main (f53b98b)

---

## 1. Контекст

FitTracker Pro 2.0 — премиальное PWA для Athlete + Coach. Утверждённая стратегия:

> **Новый frontend, существующий backend и БД.**

Перед разработкой премиального UI требуется полный аудит текущего состояния: что можно
переиспользовать, что переписать, какие API и модели БД отсутствуют для коммерческой
платформы тренеров, как безопасно мигрировать с параллельной работой старой и новой
версий.

## 2. Цели

1. Полный аудит frontend, backend, API, БД, авторизации, PWA, Telegram-интеграции и тестов.
2. Определить все существующие функции Athlete и Coach.
3. Классифицировать компоненты по KEEP / REFACTOR / REWRITE / REMOVE с объяснением.
4. Проверить совместимость существующего FastAPI с будущими интерфейсами Athlete и Coach.
5. Определить недостающие API и модели БД для коммерческой платформы тренеров.
6. Изучить ограничения offline-first и предложить безопасную архитектуру синхронизации.
7. Предложить структуру нового frontend (React + TypeScript + Vite) с единой Premium Design System.
8. Составить план миграции с параллельной работой старой и новой версий.
9. Определить необходимые E2E, API, security и performance-тесты.
10. Подготовить дорожную карту FTP-030–FTP-034 с зависимостями и критериями приёмки.

## 3. Границы и ограничения

- Не переписывать приложение в рамках этого тикета.
- Не менять production, не удалять код и данные, не выполнять миграции БД и deploy.
- Работа только в ветке `feature/ftp-020-architecture-audit`.
- Не перезаписывать незакоммиченные изменения.
- Артефакты — только документация в `docs/`.

## 4. Методология

- Проверка git-состояния перед началом.
- Параллельный независимый аудит по трём контурам: frontend, backend+API, docs+infra+CI.
- Каждый контур подтверждается фактическим кодом (пути, строки), а не описаниями.
- Классификация компонентов и выводы фиксируются в отчёт.
- После аудита — остановка и представление результатов на утверждение.

## 6. Критерии приёмки

- Отчёт содержит: текущее состояние, перечень переиспользуемых функций, недостающие
  API/модели, рекомендуемую структуру frontend, архитектурные риски, последовательность
  разработки, результаты проверок, блокеры и открытые решения.
- Дорожная карта содержит задачи FTP-030–FTP-034 с зависимостями, оценкой и критериями
  готовности.
- Изменения в репозитории ограничены `docs/` и `frontend/e2e/premium-shell.spec.ts`
  (если требуется правка теста — только в согласованном объёме).
- Результаты проверок (typecheck/lint/test/build/E2E/contract) выполняются в `frontend`
  и фиксируются с фактическими логами, либо явно помечаются «не выполнялось».

## 7. Результат

Аудит завершён, отчёт и дорожная карта созданы. Дальнейшая разработка Premium UI —
отдельные PR (FTP-021 B–G и FTP-030–FTP-034) с согласованием на каждом этапе.
